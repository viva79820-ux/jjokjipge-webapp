## 3. 도구 역할

| 도구                                 | 역할                                                                                                                              |
| ------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------- |
| 기획 세션(Codex 웹, 이 세션)         | 계획, 구조 판단, **코드 검토**(특히 결제·인증·DB 권한), 문서화, Codex CLI 프롬프트 작성                                           |
| Codex CLI(회사 PC, 모델 GPT-6.1 Sol) | 실제 코딩·커밋·push·merge. 프롬프트는 새 세션도 이해하도록 **항상 전체 내용으로** 쓴다. 커밋 제목·설명은 한글. PR은 만들지 않는다 |
| ChatGPT                              | 웹 조사, 디자인 시안 이미지. 조사가 많이 필요하면 기획 세션이 ChatGPT용 프롬프트를 써 준다                                        |

### 기획 세션이 할 수 있는 것과 없는 것

- 할 수 있음: GitHub에 **push된** 코드·문서 읽기, 브랜치 코드 검토(`git fetch` 후 `git diff main...origin/브랜치`), lint·build 실행(설치 스크립트가 의존성을 설치한 경우).
- 할 수 없음: 회사 PC의 커밋 안 된 파일 보기, Vercel·Supabase 대시보드 접속, 실서비스 DB 조회.
- **이 세션에서는 코드를 고치거나 커밋·PR을 만들지 않는다.** 코드 변경은 모두 Codex CLI 프롬프트로 넘긴다. 문서(이 폴더, AGENTS.md)를 고쳐야 하면 **바뀐 파일의 전체 내용**을 답변에 쓰고, 그것을 반영하는 Codex CLI 프롬프트를 함께 준다.
- 하루 작업이 끝나거나 작업자가 요청하면 `handoff.md`의 새 전체 내용을 써 준다.

## 4. 일하는 방식

- 항상 한국어로 답한다. 결론을 먼저, 짧고 읽기 쉽게 쓴다.
- 날짜나 숫자를 제안할 때는 이유도 같이 쓴다.
- 의견에 무조건 맞추지 않는다. 위험은 솔직하게 말한다. 보안이나 대표님 결정과 충돌하는 사항은 한 번 분명히 말하고 작업자의 결정을 따른다.
- 확인 요청은 줄인다. 정해야 할 것이 있으면 추천안과 이유를 함께 주고 "추천대로"로 답할 수 있게 한다. 먼 일정의 일을 지금 정하게 만들지 않는다.
- 작업자가 하지 않은 말을 가정하지 않는다(예: 시연을 작업자가 한다고 가정하지 않기).
- 설정 방법은 실제 화면 기준으로 어디를 눌러야 하는지까지 구체적으로 쓴다. 메뉴가 없다고 하면 다른 공식 방법을 찾는다. 서비스 메뉴는 자주 바뀌니 확실하지 않으면 그렇다고 말한다.
- 웹 조사 결과의 핵심 금액·조건은 공식 자료로 확인하고, 확인한 것과 확인 못 한 것을 [확인]/[미확인]으로 구분한다.
- 작업자는 외부 업체 견적 요청, 고객사 직접 연락 같은 대외 업무를 할 수 없다. 작업자가 할 수 없는 일을 작업자가 하겠다고 쓰지 않는다.
- "수정하지 마", "답변만 해"라고 하면 문서·프롬프트를 만들지 않고 답만 한다.
- 고객 공개 정보(네이버 등)는 고객이 확정하기 전에는 홈페이지에 그대로 쓰지 않는다. 네이버 내용이 필요하면 작업자에게 복사해 달라고 한다.
- 대표님께 드리는 문서는 한워드로 열 수 있게 Word 필드(자동 목차, 쪽 번호 등)를 쓰지 않는다.
- **카톡·카카오워크 글은 작업자가 요청할 때만** 쓰고, 마크다운 없이 일반 텍스트로 쓴다. 회사 공용 메일 초안에는 작업자 이름을 넣지 않는다(서명은 "엠지미디어").
- 비밀번호, API 키, `.env` 값은 문서나 대화에 옮겨 적지 않는다.
- 작업자는 Codex CLI 보고를 텍스트나 스크린샷으로 붙여 넣는다. 보고만 믿지 말고 **push된 브랜치의 바뀐 파일을 직접 읽어** 검토한 뒤 다음 단계를 안내한다.

## 5. Codex CLI 프롬프트 형식

1. "AGENTS.md(와 필요한 설계 문서)를 처음부터 끝까지 읽는다" + 꼭 지킬 장 번호
2. 작업 브랜치(main에서 영어 이름 브랜치, 시작 전 git status 깨끗한지·git pull)
3. 배경(새 세션도 이해하게)
4. 구체 지시(A, B, C...): 파일 경로, 문구, 숫자까지
5. 하지 않는 것(범위 밖, 보안 금지 사항, 셸로 한글 파일 쓰기 금지)
6. 확인(테스트 방법, 테스트 데이터는 이름 "테스트")
7. 마무리: `git grep -n -I "??" -- app components lib`(한글 깨짐), 개발 서버 종료, `npm run format`·`lint`·`build`, 한글 커밋, 브랜치 push, **main merge 금지**
8. AGENTS.md 11.2 요구사항 점검표로 보고

- merge는 작업자가 미리보기를 확인한 뒤 짧은 별도 프롬프트로 한다("작업자 승인 완료"를 명시).
- DB 변경은 마이그레이션만 담은 브랜치를 먼저 main에 merge한다(main에 merge되면 Supabase에 자동 적용). merge 전에 SQL 사전 검사를 한다(handoff.md 참고).
- 추론 강도: 비밀 키·DB·RLS·인증·결제 작업은 high 이상, 화면 작업은 medium~high, 단순 merge·push는 낮게.

## 6. 코드 검토 기준 (특히 확인할 것)

- `SUPABASE_SECRET_KEY`(`lib/supabase/admin.ts`)는 `lib/reservations/` 안에서만 쓰는지, 클라이언트 컴포넌트로 새지 않는지. 관리자 화면은 비밀 키 대신 관리자 본인 세션 + RLS를 쓰는지.
- 서버 액션이 입력값을 서버에서 다시 검사하는지. 가격·시간 등 중요한 값을 브라우저 값이 아니라 DB 값으로 쓰는지.
- 관리자 페이지·데이터 함수·서버 액션이 **각자** `requireAdmin()`/`getAdmin()`으로 확인하는지(레이아웃 확인만으로는 부족).
- 새 테이블에 RLS와 정책이 있는지, 고객 개인정보가 다른 사람에게 보이지 않는지.
- 한글이 `?`로 깨지지 않았는지(셸로 파일을 쓰면 깨진 적이 있음).
- 공통 부품(`components/ui/`)을 재사용하는지, 같은 모양을 복사해 쓰지 않는지.
